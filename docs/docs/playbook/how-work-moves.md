# How Work Moves Through the System

<span class="badge badge--success">Engineers</span> <span class="badge badge--warning">Program Managers</span>

> **"If work can't be traced, it can't be trusted."**

## What We Do

Every change:

- **Has intent**  -  we know why it exists
- **Produces evidence**  -  we can show what happened
- **Can be explained after the fact**  -  auditable without archaeology

## The Anatomy of Traceable Work

```
Intent → Change → Evidence → Outcome
   ↓        ↓         ↓          ↓
 "Why"   "What"   "Proof"    "Result"
```

Each link in this chain should be followable by someone who wasn't there.

## What This Looks Like

- Commits reference intent (ticket, RFC, decision record)
- Changes are small enough to review meaningfully
- Deployments are recorded with context
- When someone asks "why is it like this?" - there's an answer

## What This Is NOT

| This Is NOT | This IS |
|-------------|---------|
| Extra paperwork | Clarity that prevents rework |
| Approval theater | Evidence that builds trust |
| Micromanagement | Visibility that enables autonomy |
| Bureaucracy | The cost of working at scale |

## The Payoff

When work is traceable:

- Onboarding is faster (context exists)
- Debugging is easier (history is legible)
- Audits are boring (evidence is already there)
- Trust accumulates (because receipts exist)

## Maps To

**Understanding Optimization**  -  Legibility isn't overhead. It's how distributed teams stay coherent.
