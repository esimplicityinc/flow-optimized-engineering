# FOE Maturity Self-Assessment

This assessment helps you understand where your organization actually operates - not where you wish it did, or where your tooling suggests it should.

:::warning Honest Assessment Over High Scores
The value of this assessment comes from honesty, not from achieving high scores. A team that accurately identifies Level 1 operation is in a better position than one that claims Level 3 without evidence.
:::

## How to Use This Assessment

1. **Answer based on typical behavior**, not best-case or aspirational scenarios
2. **Consider what happens under pressure** - maturity often drops when stress increases
3. **Look for the lowest consistent level** - you operate at the level that holds under strain
4. **Discuss as a team** - different perspectives reveal different realities

## Understanding Assessment

### Q1: Where does critical system knowledge live?

| Level | Answer |
|-------|--------|
| **0** | In specific people's heads. When they're unavailable, work stops. |
| **1** | Partially documented, but finding information requires asking around. |
| **2** | Documented in known locations. New team members can find what they need. |
| **3** | Generated by the system. Documentation updates automatically as part of work. |
| **4** | Self-maintaining. Knowledge structures adapt as the system evolves. |

### Q2: What happens when someone leaves the team?

| Level | Answer |
|-------|--------|
| **0** | Panic. Critical knowledge disappears. Projects stall. |
| **1** | Disruption. We can recover but it takes weeks of archaeology. |
| **2** | Manageable transition. Documentation and processes fill most gaps. |
| **3** | Smooth handoff. The system contains most of what they knew. |
| **4** | Minimal impact. Knowledge is in the architecture, not the people. |

### Q3: How do you explain your system to a new team member?

| Level | Answer |
|-------|--------|
| **0** | Shadow someone for weeks. Hope they absorb enough tribal knowledge. |
| **1** | Point them at some docs and schedule meetings with key people. |
| **2** | Follow the onboarding guide. It covers the standard paths. |
| **3** | Show them how to learn from the system. It reveals its own structure. |
| **4** | The system guides them. Learning is built into the interface. |

### Q4: Can three different team members explain the same process consistently?

| Level | Answer |
|-------|--------|
| **0** | No. You get three different answers, all partially correct. |
| **1** | Somewhat. The broad strokes match but details vary. |
| **2** | Yes, for documented processes. Novel situations still diverge. |
| **3** | Yes. The system enforces consistency. |
| **4** | Yes, and the system detects when understanding drifts. |

### Q5: How current is your documentation?

| Level | Answer |
|-------|--------|
| **0** | What documentation? Or: exists but no one trusts it. |
| **1** | Some docs are current. You have to know which ones to trust. |
| **2** | Regularly updated as part of change processes. Mostly reliable. |
| **3** | Generated from the system. Current by definition. |
| **4** | Automatically validated and corrected. |

## Fast Feedback Assessment

### Q6: When do you typically discover problems?

| Level | Answer |
|-------|--------|
| **0** | In production. Often from users or monitoring alerts. |
| **1** | During testing, but testing happens late in the process. |
| **2** | In CI/CD. Automated checks catch most issues before merge. |
| **3** | While coding. Immediate feedback on problems. |
| **4** | Before coding. The system suggests issues with proposed approaches. |

### Q7: How long does it take to determine if a change is safe?

| Level | Answer |
|-------|--------|
| **0** | We don't really know until it's in production for a while. |
| **1** | Hours to days. Manual testing and review. |
| **2** | Minutes to hours. Automated tests provide confidence. |
| **3** | Seconds to minutes. Continuous feedback during development. |
| **4** | Immediate. Safety is built into the development process. |

### Q8: What does your team learn from a typical deployment?

| Level | Answer |
|-------|--------|
| **0** | Whether it worked. Sometimes nothing until a problem surfaces. |
| **1** | What broke and roughly why. Post-hoc investigation. |
| **2** | Whether it matched expectations. Metrics confirm or contradict. |
| **3** | How the system behaved. Rich telemetry provides insight. |
| **4** | How to improve the process. Each deployment informs the next. |

### Q9: How quickly can you detect a production problem?

| Level | Answer |
|-------|--------|
| **0** | When users complain or something obviously breaks. |
| **1** | Through alerts, but they're noisy or delayed. |
| **2** | Within minutes through defined monitoring. |
| **3** | Immediately through continuous observation. |
| **4** | Before users notice, often with automatic mitigation. |

### Q10: How long between writing code and knowing if it works?

| Level | Answer |
|-------|--------|
| **0** | Days to weeks. Feedback is batched at phase gates. |
| **1** | Hours to days. Testing and review cycles add delay. |
| **2** | Minutes to hours. CI provides relatively quick feedback. |
| **3** | Seconds to minutes. Development environment provides immediate signal. |
| **4** | Continuous. The system evaluates code as you write it. |

## Confidence Assessment

### Q11: Would your team deploy on a Friday afternoon?

| Level | Answer |
|-------|--------|
| **0** | Absolutely not. We'd never recover from problems over the weekend. |
| **1** | Only if forced. We'd be nervous all weekend. |
| **2** | For routine changes, yes. The process is reliable. |
| **3** | Yes, with confidence. We'll know immediately if something's wrong. |
| **4** | Day doesn't matter. Deployment is safe and reversible anytime. |

### Q12: How do teams make decisions about technical risk?

| Level | Answer |
|-------|--------|
| **0** | Escalate to leadership. Avoid risk when possible. |
| **1** | Discuss in meetings. Decisions are based on opinion and experience. |
| **2** | Follow established patterns. Risk is managed through process. |
| **3** | Use data from the system. Decisions are evidence-based. |
| **4** | Trust the guardrails. The system prevents dangerous choices. |

### Q13: What happens when you discover an unexpected problem?

| Level | Answer |
|-------|--------|
| **0** | Crisis mode. All hands on deck. Investigation takes days. |
| **1** | Concern. We can investigate but it takes significant effort. |
| **2** | Managed response. Runbooks guide initial actions. |
| **3** | Quick resolution. The system helps us understand and fix. |
| **4** | Routine. Often handled before becoming a real problem. |

### Q14: How confident are you in your test coverage?

| Level | Answer |
|-------|--------|
| **0** | What tests? Or: we have tests but don't trust them. |
| **1** | Partially covered. Critical paths are tested, we think. |
| **2** | Well covered for known scenarios. We trust the test suite. |
| **3** | Comprehensive and evolving. Coverage gaps are visible and tracked. |
| **4** | Self-improving. The system identifies and addresses coverage gaps. |

### Q15: Can you rollback a bad deployment?

| Level | Answer |
|-------|--------|
| **0** | Theoretically. We've never actually done it successfully under pressure. |
| **1** | Yes, but it's manual and stressful. |
| **2** | Yes, it's a documented process that we've practiced. |
| **3** | Instantly. Rollback is built into the deployment process. |
| **4** | Automatically when needed. The system detects and responds. |

## Scoring Guidance

### Calculating Your Assessment

1. **For each question, identify your honest answer** based on typical - not best-case - behavior
2. **Note the distribution of your answers** across levels
3. **Your operational level is the lowest level where you consistently operate** under normal conditions

### Interpreting Results

:::tip Healthy Patterns
- **Mostly Level 1-2 with improvement trajectory**: Common and healthy
- **Level 2-3 with occasional drops to Level 1**: Normal under pressure
- **Consistent Level 3**: Strong FOE implementation
- **Mixed across optimizations**: Normal - improvement targets become clear
:::

:::warning Concerning Patterns
- **Claims of Level 3-4 that don't survive pressure**: Overestimation
- **Level 0 answers in critical areas**: Immediate risk
- **Wildly inconsistent answers within teams**: Alignment problem
- **Consistent Level 4 claims**: Usually overestimation - verify with evidence
:::

### What To Do With Results

1. **Identify the lowest consistent level** - that's your baseline
2. **Look for optimization gaps** - where is feedback slowest? Understanding weakest? Confidence lowest?
3. **Choose one area to improve** - sustainable progress beats broad initiatives
4. **Reassess after changes** - did behavior actually shift?

---

## Key FOE Insight

:::info The Goal Is Not Level 4
**The goal is not to reach Level 4. The goal is to operate honestly at your current level and reduce surprise.**

Maturity is not prestige. It is predictability under change.

An organization that honestly operates at Level 2 with continuous improvement is healthier than one that claims Level 4 but can't explain how their system works.

The best use of this assessment is not to produce a number. It's to enable honest conversation about where friction exists and what would help.
:::

## Reassessment Cadence

- **Quarterly** for teams actively improving
- **After major incidents** to understand what level you operated at under stress
- **When team composition changes significantly** to verify knowledge transfer
- **Never as a compliance exercise** - the moment it becomes mandatory, it loses value
